### <a name="_3bfxc9a45514"></a>**Функциональные требования**
MVP охватывает подачу заявки действующим клиентом в интернет-банке и обращение потенциального клиента с сайта. Горизонт MVP интернет-банка — шесть месяцев. Депозитный бэк-офис обрабатывает принятые заявки. Автоматическое открытие вклада относится к целевому состоянию через год. ### <a name="_qmphm5d6rvi3"></a>**Решение**

[C4: контекст](deposit-context.svg) · [C4: контейнеры интернет-банка и АБС](deposit-containers.svg)

На диаграмме контекста показаны системы и участники MVP. На уровне контейнеров отдельно раскрыты границы интернет-банка и АБС. Стрелки показывают, кто выполняет подписанное действие или передаёт данные. Карточки Kafka в обоих видах обозначают одну платформу обмена.

**Общие ставки по депозитам.** Кредитный бэк-офис рассчитывает ставки в Excel. Команда АБС добавляет импорт и публикацию в существующий клиент на Delphi. Автор расчёта импортирует файл с новыми значениями. АБС хранит загруженные и опубликованные ставки в Oracle. Право публикации принадлежит владельцу условий депозитного продукта. Для MVP предполагаем, что эту роль выполняет депозитный бэк-офис.

**Доставка общих ставок в каналы.** При каждой публикации АБС передаёт через Kafka полный набор общих ставок с номером версии. Команда интернет-банка сопровождает обработчик Kafka и витрину в отдельной схеме MS SQL. Этот выбор использует знакомую команде СУБД и даёт обоим каналам единый источник опубликованных условий. Обработчик обновляет общую таблицу ставок. Он применяет набор целиком, только если его версия новее текущей. При прерванной загрузке каналы продолжают показывать предыдущую версию. Депозитный сервис, который уже принимает заявки, читает витрину. Его публичный HTTPS-интерфейс возвращает сайту только общие ставки. Сайт обращается к сервису напрямую. Веб-приложение интернет-банка через авторизованный интерфейс получает также предложения вошедшего клиента.

**Персональные предложения.** До подачи заявки отдельный процесс в АБС автоматически определяет получателей каждого предложения. Для группового предложения процесс выбирает клиентов соответствующей группы, для индивидуального — конкретного клиента. В обоих случаях АБС передаёт через Kafka готовое предложение с идентификатором получателя. Обработчик сохраняет персональные предложения в отдельной таблице витрины. Депозитный сервис выбирает их по идентификатору клиента из доверенного контекста сессии интернет-банка. Публичному сайту доступны только общие ставки. Когда клиент подаёт заявку, условия по ней подтверждает в АБС менеджер депозитного бэк-офиса (F2).

**СМС-подтверждение подачи.** За формирование и проверку одноразового кода отвечает сервис приёма заявок команды интернет-банка. Он привязывает код к заявке с выбранным счётом и суммой. Если клиент изменил эти данные, сервис запрашивает новое подтверждение. Банковский СМС-шлюз передаёт сообщение оператору связи для доставки клиенту. Команда банка может реализовать этот сценарий без доработки ядра подрядчиком (+R2).

**Единый приём из двух каналов.** Сайт и монолит интернет-банка вызывают один сервис приёма по HTTPS. Для сайта он принимает выбранный продукт, Ф. И. О. и телефон для звонка. Для интернет-банка он проверяет СМС-код, привязанный к параметрам депозитной заявки. Сервис направляет каждый вид заявок в свой поток Kafka и подтверждает приём каналу после подтверждения записи репликами. С этого момента дальнейшая доставка — ответственность банка. При сбое или потере ответа повтор подачи использует тот же идентификатор операции, чтобы клиент получил результат по той же заявке.

**Получатели обращений.** CRM подписывается на обращения с сайта. При повторной доставке потребитель находит имеющееся обращение по идентификатору. Позицию чтения он подтверждает после регистрации. Менеджер видит одно обращение для звонка. За оценку, выбор способа подключения и сопровождение потребителя отвечает подрядчик CRM-платформы кол-центра. Он может расширить приложение или разместить адаптер. Для разработки расширения на Java банк при необходимости привлекает специалистов команды АБС. АБС получает отдельный поток подтверждённых заявок интернет-банка.

**Регистрация заявки в АБС.** Команда интернет-банка передаёт в Kafka подтверждённую заявку с устойчивым идентификатором. Команда АБС разрабатывает и сопровождает входящий адаптер в границах АБС. Адаптер читает сообщение из Kafka и передаёт заявку на регистрацию для работы менеджера. АБС обеспечивает уникальность записи по идентификатору заявки. Адаптер фиксирует позицию чтения после успешной регистрации или подтверждения, что заявка с этим идентификатором уже зарегистрирована. После сбоя обработку можно продолжить без повторного создания заявки. Клиент узнаёт о подтверждении ставки и об открытии вклада из отдельных СМС.

| Команда интернет-банка | Выбор счёта и суммы, единый депозитный сервис, СМС-код и запись заявок в Kafka. Владеет обработчиком условий и витриной MS SQL, следит за актуальностью версий, предоставляет публичный и авторизованный интерфейсы чтения. |

| Кредитный и депозитный бэк-офисы, кол-центр и отделения | Проверка прав на импорт и публикацию, правил назначения персональных предложений, обработки заявок, обратного звонка и идентификации. |

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Рассматривали журнал заявок в MS SQL интернет-банка с фоновым обработчиком. Он позволил бы использовать имеющуюся БД. Для MVP выбрали Kafka с учётом предпочтения банка развивать дальнейший обмен сообщениями на этой платформе (+R6).

Для общих ставок рассматривали выгрузку по расписанию. Она добавляет задержку до следующего запуска. Отправка при публикации позволяет обновить условия сразу после доставки сообщения и использует Kafka, уже выбранную для депозитных заявок.

Синхронная регистрация напрямую в CRM или АБС упростила бы интеграцию, но при остановке получателя соответствующий канал перестал бы принимать обращения. Единый сервис с Kafka сохраняет возможность приёма, пока доступен путь до надёжной записи.

**Недостатки, ограничения, риски**

Приём заявки теперь зависит от доступности сервиса приёма и Kafka. Банку потребуется обеспечить репликацию, следить за отставанием обработчика и выбрать срок хранения сообщений, достаточный для восстановления АБС и разбора накопившихся заявок. При повторной доставке одной заявки АБС должна зарегистрировать её однократно.

Для эксплуатации нужны контроль задержек обоих потребителей, оповещение о заявках, которые не удалось обработать, и безопасный повтор после устранения ошибки. Для каталога требуется контролировать версию и время последнего обновления. При сбое отправки из АБС опубликованная версия должна оставаться доступной для повторной передачи. Допустимое время показа прежней ставки и порядок снятия просроченных персональных предложений согласуются с владельцем продукта.

Размещение компонентов в резервном ЦОД, сохранность принятых заявок при потере площадки, доступность данных для выбора счёта и допустимое время переключения требуют отдельного решения по инфраструктуре. Доступность 99,9% и время отклика предстоит подтвердить измерениями.
